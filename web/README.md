# web

kc-sim の Web UI。
シミュレーションはブラウザ内で動く(sim-core の wasm を Web Worker で実行する)。
サーバの Cloudflare Worker が `dist/` を静的アセットとしてデータ API と同じ場所で配信するので、UI は同一オリジンの `/api/v1/*` を呼ぶ。
poi プラグイン(`../poi-plugin-sim`)はこのページを iframe に埋め込み、poi の艦隊とマスターデータを `postMessage` で送って、表示するビューを指定する(プロトコルは [`shared/embed/protocol.ts`](../shared/embed/protocol.ts)。説明はプラグインの README にある)。

## ナビゲーション

VS Code 風の構成で、ブラウザとプラグインは 1 つのモデル(`src/app/nav.tsx`)を共有し、1 つのコンポーネント(`src/ui/AppChrome.tsx`)で描画する。
左のアクティビティバー(アイコンと短い名前、64 px)で機能を切り替え、上の行で選択中の機能のビューを切り替える(ビューが 1 つしかない機能では、上の行にタイトルを出す)。
右端にはバージョンを出す。

| 機能(バー) | ビュー(上の行) |
|---|---|
| シミュ(シミュレーション) | 出撃(ワークスペース。マップ、艦隊エディタ、結果をページをスクロールせずに 1 画面に収める)、海域(マップとルーティング)、敵艦(マスター ID ごとに 1 行。エリートと旗艦の印、ステータス、装備、サーバが推定した隠しステータス。`src/app/enemy/`)、計算設定(サーバの推定値を使うか、観測を優先する遭遇数)。プラグインでは観測ログと送信設定も加わる |
| 任務 | ビュー 1 つ(前提任務のツリー。後述) |
| 資源 | プラグインのみ: 推移 / 増減 (イベント) / 増減 (日別) |
| 設定(歯車、最下部) | ビュー 1 つ: サンプルデータの切り替え、プリセットの削除、データキャッシュの消去、設定のリセット |

ページを直接開いたときは、ページ自身が持つ機能でバーを描く(観測ログと送信設定を除いたシミュ、任務、設定)。
プロトコル v3 以降のプラグインの中では、バーはプラグインが描き、表示するビューをプラグインが送る(`view`)。
ページが自分で画面を移動したとき(海域 →「戦闘シミュ」/「出撃シミュ」、`nav.go({ view: "sortie", … })`)は、プラグインがその移動を受け取る。
このときページはバーを描かない。
古いプラグイン(v2。自前のヘッダ行が 1 つある)の中では、ページはプラグインのヘッダの下にバーを描く。
現在のビューは `kcsim:view` に保存する(機能を切り替えると、同じセッション内ではその機能で最後に見ていたビューに戻る)。
古い `kcsim:tab`(出撃 / 海域 / 敵艦 / 任務 / 設定のバー、`estimate` → `enemy`)は 1 回だけ移行する。
文書の幅が 928 px(`--breakpoint-lg`)以上になると 2 カラムのレイアウトになる。
プラグインの 1024 px のウィンドウでは iframe の幅が 928 px(1024 − バーの 96 px)になり、このページを 1024 px で直接開いたとき(自前のバーつき)のコンテンツ幅と一致する。

## コマンド

必要なもの: [bun](https://bun.sh) ≥ 1.3、`wasm32-unknown-unknown` ターゲットを入れた Rust、`wasm-pack`。

```sh
bun install
bun run dev                    # vite on http://localhost:5173, /api → http://127.0.0.1:8787 (KCSIM_API to change)
bun run build                  # wasm-pack (../sim-core) + vite → dist/
SKIP_WASM_BUILD=1 bun run build   # reuse an existing ../sim-core/pkg (also for dev)
bun test
bun run typecheck
```

`bun run dev` は待ち受けを始める前に `../sim-core/pkg` をビルドし、`../sim-core/src`、`Cargo.toml`、`Cargo.lock`、`sim_core_types.d.ts` が変わるたび(編集や `git merge` / `pull`)に再ビルドする。
新しい pkg ができるとページを再読み込みし、ビルドに失敗するとエラーをオーバーレイに出す。
HMR で TypeScript だけがすぐ更新されるため、再ビルドしないと、新しいランナーが古い wasm の出力しないサマリのフィールドを読んでしまう。
`SKIP_WASM_BUILD=1` のときは既存の pkg を配信し、変更を監視しない。

`dist/` には `index.html` と `assets/`(ハッシュ付きの JS、CSS、`sim.worker-*.js`、`sim_core_bg-*.wasm`)が入る。
`../server/dist/maps` があれば(`cd ../server && bun run export:bundle`)`maps/` も入る(`/api` が失敗したときに UI が読む静的なマップのバンドル)。

スクリプトは次のとおり。

- `bun run sample`: `@kancolle/data` から `src/sampleState.json` を再生成する。
- `bun run screenshots`: `docs/screenshots/` または `SHOTS_DIR` に撮影する。
  ファイル名の接頭辞は `SHOTS_PREFIX` で指定する。
  撮った画像のうちリポジトリに入れるのは README が使うものだけにする。
  API が落ちているとき(たとえば `KCSIM_API=http://127.0.0.1:9`)は静的バンドルを使う。
  撮影対象のマップの敵編成が API にないとき(KCNav を取り込んでいないローカル D1)は、マップのデータをバンドルから取る。
  次のいずれかに当たると失敗する: バーが シミュ / 任務 / 設定 でない、ビューが 出撃 / 海域 / 敵艦 / 計算設定 でない、サンプルの艦隊が一度もボスに到達しない、1280×800、1200×710、1024×600 のいずれかで出撃タブのページかタブの内容がスクロールする。
- `bun run audit [--offline]`

## 出撃ワークスペース

左の列には次のものを置く。

- 編成(プリセットの選択と ⋯ メニュー。名前、司令部レベル、poi からの取り込み(fleet 1〜4、または 連合 = fleet 1 + 2)、新規 / 複製 / 入出力 / 削除)
- 艦隊(通常艦隊 / 機動部隊 / 水上部隊 / 輸送護衛部隊 / 遊撃部隊)
- 艦隊の上の 主力 / 随伴 / 支援 / 友軍 / 基地 のタブ

右の列には結果と、その下のシミュレーターのツールバーを置く。
ツールバーには使う順に左から、海域(イベント海域では難易度も)、出撃 / 単一戦闘(単一戦闘はノードと敵編成つき)、条件(スライダーのアイコン)、自動(チェックボックス)、実行(再生アイコンと回数。進捗に応じて塗りつぶされる)が並ぶ。
出撃モードでは、マップの隣で 目標マス も選べる(既定はボス。マップごとに `kcsim:workspace` に保存する)。
出撃はそのノードで終わり、主要な率(到達 / 突破 / S勝利 / 旗艦撃沈、ゲージ)はボスの代わりにそのノードで数える(sim-core の `config.target`)。
条件には、マップの規則の `select` ノードごとに 能動分岐 の選択肢が 1 つある(選択肢は行き先で示す)。
この選択もマップごとに保存する。
選択が保存されていないノードは `defaults.select`(なければ最初の選択肢)を使う。
目標マス が設定されていて、選んだ選択肢では目標マスに到達できないときは、到達できる最初の選択肢を使う(`resolveSelects`)。
敵連合艦隊(たとえば 6-5 M)は随伴艦隊も含めて送り、6 対 12 または 12 対 12 で戦う(陣形 11〜14 → 第一〜第四警戒航行序列)。
結果には敵の主力艦隊、随伴艦隊の順に並ぶ。

左の列の艦隊パネルは、1 行の艦隊サマリ(アイコンで制空、速力、索敵 Cn1〜4、ドラム缶、電探)と、ゲームと同じ 2 × 3 のグリッドに並ぶ 6 隻からなる。
パネルの幅が 36rem 未満のとき(たとえば 1024 / 1200 px)は 1 列にしてパネル内でスクロールさせ、名前が読める幅を保つ。
各艦はヘッダ(番号、艦種、名前、Lv)の下にスロットの列(装備アイコン、名前、★、熟練、搭載)を 1 つ持つ。
改修、士気、ステータスは ⋯ の中にある。

右の列の結果は、主要な率を 0〜100 % の共通の目盛りのバーで示す(ボス到達はボスでのランクで色分けする。突破 = 出撃あたりのボス A 以上、S勝利 = 出撃あたりのボス S 以上、大破撤退)。
その下に補助的な数値(周回、旗艦撃沈、資源/出撃、入渠、護衛退避、出撃間の待ち)と詳細のタブが並ぶ。
詳細のタブは次のとおり。

- マス: ランクで色分けした到達のバー、ノードごとの 退避 と 大破撤退
- 経路: 辺の太さが通過率を表す経路図
- 損耗: 艦ごとの損傷、入渠時間、ボーキ、ダメージコントロール、退避
- 資源
- ゲージ(ゲージを設定したときのみ)
- 前提

出撃の 条件 には 5 つのタブがある(`src/app/sim/conditions/`)。
撤退、消費、ゲージ、マス、資源、艦隊 の設定は `kcsim:workspace` に保存し、ゲージ / マス と 基地空襲 / 友軍 のノードはマップごとに `sortieMaps` に保存する。
開始、フラグ、陣形は保存しない。

- 基本: 夜戦の方針、撤退(大破撤退 `onHeavy`、ダメコン所持艦は進撃 `allowDamecon`、中破撤退 `onModerate`、護衛退避 `useFcf`。旗艦の指揮施設 107 / 272 / 413 を表示する)、ボス前に使う消耗品(洋上補給 `policy.underway`、戦闘糧食 `policy.rations`)、開始、能動分岐、フラグ、ノードごとの陣形、フェーズ / ゲージ番号、回数とシード。
- 艦隊(`conditions/ExtraFleets.tsx`。単一戦闘の 条件 にもある): 道中支援と決戦支援のオン/オフと種別(編成から / 航空 / 砲撃 / 長距離雷撃 / 対潜)→ `SortieInput.support {node, boss}`(単一戦闘では `BattleInput.support`。決戦支援はボスで出る)。友軍艦隊のオン/オフ、到着率 %、ノード(既定は 目標マス)→ `friendFleet`。基地空襲は、到着時に空襲を受けるノード、確率、空襲してくる敵編成のノード → `baseRaids`(単一戦闘では、選んだ編成が飛行隊を持つすべての基地を空襲する。`baseRaid`)。
- マス: 各ノードのあとの 進撃 / 撤退 / 強行(`policy.advance`: retreat / push)、戦闘ノードごとの 煙幕(`policy.smoke`。`shared/sim/nodeEffects.ts` で阻塞気球があるとされたノードには 気球 の印を付け、`SortieNode.balloons` として送る)、資源マスと揚陸マスでの獲得(`SortieNode.resource`)、渦潮での損失(`SortieNode.maelstrom`)。
- ゲージ: 種別(撃破(ボス旗艦撃沈)/ HP / 輸送(TP))と残量(`gauge`)、HP ゲージの最終閾値と最終編成、TP ゲージでの輸送ドラム缶の強制と S勝利あたりの TP、追加ゲージ(`gauge.phases`: 種別、残量、フェーズ)、ゲージを割るまで持ち越す士気(`gauge.morale`)、連続出撃(`consecutive`)。
- 資源: 入渠時間が `repair.bucketAboveSec` を超えたときに使う 高速修復材、エンジンがモデル化していない出撃あたりの費用(`extraPerSortie`。支援遠征の費用はエンジンが数える。`supportCostMean`)。

資源 タブは、出撃あたりとゲージクリアあたりの燃料 / 弾薬 / 鋼材 / ボーキ / バケツ / 入渠時間の純増減(平均、中央値、90%)、入渠の費用、基地の費用、使った洋上補給 / 糧食、ノード効果を示す。
ゲージ タブは、クリアまでの出撃数(平均、中央値、90%)、上限に達した実行、士気の回復待ち、ゲージあたりの出撃数、クリアあたりの資源を示す。
遊撃部隊 は最大 7 隻の単一艦隊として扱う(`striking: true` として送る)。
7 隻で保存された 通常艦隊 は遊撃部隊として読み込む。

連合艦隊の 主力 と 随伴 は同じパネルで編集する。
陣形のリストは 第一〜第四警戒航行序列 に切り替わる(もう一方の種類の陣形が設定されていたら 単縦陣 / 第四警戒 に置き換える)。
結果には主力艦隊、随伴艦隊(「随伴 …」)の順に並ぶ。

支援 タブの道中支援と決戦支援の艦隊(各 6 隻)と、友軍 タブの友軍艦隊(7 隻。「全艦から選ぶ」で任意のマスター艦を選べる)も同じパネルで編集し、プリセットに保存する(`supportNode` / `supportBoss` / `friendFleet`)。
結果には、ノードごと(マス)の 支援 / 友軍 と基地空襲の率(防空時の制空状態と失った基地の HP はツールチップに出す)、支援の費用(資源)を出す。
単一戦闘では 支援到達 / 友軍来援 / 防空の制空 を出す。

基地 タブでは、最大 3 つの基地航空隊にそれぞれ 4 つの飛行隊を編成する(航空機のみ。艦の装備と同じ要領で選ぶ。偵察機は 4 機、それ以外は 18 機)。
各基地は 出撃 / 防空 / 待機 のいずれかにする。
出撃 の基地は、現在のマップで選んだノードに 2 波を送る(同じノードを 2 回選ぶと、そのノードに 2 波とも送る)。
基地の攻撃は艦隊の戦闘より前に、出撃でも 単一戦闘 でも行う(単一戦闘では、標的がその戦闘のノードである波だけを使う)。
防空 の基地は 基地空襲 を迎え撃つ(`LandBase.defense`)。
待機 の基地は何もしない。
空襲を設定すると、飛行隊を持つすべての基地が被害を受ける可能性がある。
飛行隊の行動半径(`api_distance`)がノードの `lbasDistance` に届かない波は取り除く(sim-core が警告を出す)。
「poi から取り込み」 は、poi にあるそのマップの海域の基地を読み込む(なければ最新の海域の基地)。
標的の選択は変えない。
艦隊の種類、随伴、支援 / 友軍艦隊、基地航空隊とその標的はプリセットに保存する。

自動実行(`src/app/sim/useSimRun.ts`)は、自動 がオンの間、シミュレーションの入力(艦、装備、マップ、難易度、モード、条件、推定値の設定。プリセットの名前とメモは含まない)が変わるたびに動く。
最後の変更から 300 ms 後に、出撃または戦闘を 10,000 回実行し直し、実行中の計算はキャンセルする。
実行 ボタンは、条件で選んだ回数(既定は 100,000)を実行する。
古い結果は薄く表示し、実行 ボタンは進捗に応じて塗りつぶす。
シードを固定しているので、艦隊を変えて比べるときも同じ乱数列を使う。
マップ、モード、条件、自動 は `kcsim:workspace` に、プリセットは `kcsim:selectedPreset` に保存する。

## 任務タブ

実装は `src/app/quests/QuestTab.tsx` で、`GET /api/v1/quests` と `shared/quest/tree.ts` を使う。
任務データはデータのバージョンごとにキャッシュする(boot ビューの `dataVersion` が応答の ETag のバージョンと等しい間は保持し、boot が失敗したときは 24 時間保持する)。
画面は全高のカード 3 枚で、各カードの中でスクロールする(1280×800 / 1200×710 / 1024×600 でページ自体はスクロールしない)。
これは `bun scripts/screenshot-quests.ts` で確認する。
このスクリプトは次の画像も書き出し、すべて 1024×600 で撮る。

- `docs/screenshots/17-quests.png`
- `18-quest-progress.png`(プラグインのカウントつきの一回限りの任務)
- `19-quest-filters.png`(絞り込んだ一覧と、選択報酬 つきの任務)
- `24-quest-doable.png`(実施可能 をオンにし、poi の状態を注入したもの)
- `25-quest-tree.png`(「すべて開く」のあとの A88 のツリー)

完全に展開した A88 か B117 のツリーで、タイトルの幅が約 8 文字に満たない行があるときも、スクリプトは失敗する。
タブに出すのは、UI 自体から読み取れない情報だけである。
枠付きの状態バッジ、見ればわかることを言い直すキャプション、データの出所についての注釈は置かない。

- **一覧:** コード / 名前 / ID で検索でき、3 つのドロップダウンによる絞り込み(`QuestFilters.tsx`。`shared/quest/filter.ts` を使う)と組み合わせられる。
  種別(単発 / デイリー / ウィークリー / マンスリー / クォータリー / イヤリー / 期間限定。キーは `freq`)と分類(A 編成 … G 改装、その他。キーは `cat`)は、どちらも wiki のコード(`Bq3`、`2610B3`、`L2610F2`、`Cs8` 季節限定 → 期間限定)から決める。
  状況(未開放 = まだ解放されていない、未達成 = 受注可、遂行中 = 遂行中・達成、達成済、不明)もあり、poi の任務の状態があるときだけ出す。
  各選択肢には、ほかの絞り込みと検索を適用したうえで何件残るかを出す。
  その下に「実施可能」のトグル(後述)があり、これもほかの絞り込みを適用したうえで残る件数を出す。
  オンのときは、除外した 不明 の任務の件数を注記する。
  poi の任務の状態と所持リストがないときは無効になる(「poi 接続時のみ」)。
  絞り込みは `kcsim:questFilter` に保存する(以前の 未達成 = 受注可・未開放 を表す保存済みの `open` は 未開放 + 未達成 として読み込み、`doable` のない保存済みの絞り込みはトグルをオフにして読み込む)。
  選択中の任務は `kcsim:quest` に保存する。
  任務ごとに状態のドットを付け、実施可能 な任務にはチェックマーク(条件の一部が確認できなかったときは代わりに「条件未確認」)を付ける。
  行のツールチップには説明、条件、報酬の要約を出す。
- **任務:** ヘッダに 種別 と状態(ドットとテキスト)を出す。
  本文は説明、構造化したクリア条件(オーバーライド、なければ kcwiki-quest-data)、オーバーライドの `note` の順に並ぶ。
  poi のデータがあるときは、実施可能 でない任務の不足分(「不足: 潜水空母/潜水艦 0/2」)と、確認できなかった条件をプレーンテキストで出す。
  続いて報酬(`QuestRewards.tsx`。プレーンテキストで、資源は色付きのドットと通常色の数値、固定のアイテムは「、」でつなぎ、選択報酬 はグループごとに「選択1: A / B / C」を 1 行。このとき KC3 のメモにある `[獲]` の部分は隠す)、進捗、前提任務のツリー(後述)が並ぶ。
  最下部には「出典:」の行が 1 つあり、この任務のデータの出所(オーバーライドの参照ページ、kcwiki-quest-data、KC3Kai、kcanotify)にリンクする。
- **前提任務のツリー**(`PrerequisiteTree.tsx`。`shared/quest/tree.ts` の `prerequisiteOutline` を使う): 前提のつながりは 2 種類あり、描き分ける。
  - **連鎖:** 前提がちょうど 1 つの任務は、その前提を*同じ*インデントで次の行に置き、2 つの状態のドットを縦線で結ぶ。
    縦線は「下の任務が前提」という意味である。
    直線的なつながり(B74 → A71 → B72)は 1 本の列として読める。
  - **分岐:** 前提が 2 つ以上ある任務は、各前提を 1 段(10 px)深くインデントし、▸ のトグルの下から肘形のガイド線でつなぐ。
    分岐は ID 順に並べる。

  そのため、インデントが深くなるのはグラフが分かれる箇所だけになる。
  A88 / B117 のような 40 件を超えるツリーも 5 段以内に収まり、1024×600 ですべてのタイトルが約 8 文字以上の幅を保つ(A88 は、普通のツリー表示だと 16 段になっていた)。
  対象の任務自身の前提が最上位に来る(前提が 1 つだけでも同じ)。
  グラフは DAG なので、2 回目に出てくる任務(共通の祖先)は部分木を繰り返さず、薄い 1 行の参照(↰)にする。
  参照をクリックすると、元の行まで開いてそこへスクロールし、強調表示する。
  ▸ のトグルは連鎖の先頭と、分岐を持つすべての任務に付く(連鎖の途中の行には付かない。連鎖は先頭で畳む)。
  閉じた行には、隠している任務の件数を出す(「+12」)。
  初期状態では、2 段目のインデントまでと、受注可 / 遂行中 の任務に至るすべての分岐(プレイヤーの最前線)を開き、前提がすべて 達成済 / 達成 の行とそれより深い行を閉じる。
  「すべて開く」 / 「畳む」で、全展開とこの初期状態を切り替える。
  循環は閉じる辺で切り、未知の ID はそのまま表示する(どちらもツリーの下に注記する)。
  行をクリックすると、その任務を選択する。
- **必要なもの:** 「未達成の前提任務を含む」として、ツリー内のまだクリアしていない任務の条件に出てくる艦と装備を、条件ごとに 1 行にまとめる。
  同じマスター艦に解決される艦の行(オーバーライドのマスター ID と上流の名前、駆逐 / 駆逐艦 のように同じ艦を指すもの)は 1 行にまとめ、解決できなければ名前が同じ行をまとめる。
  艦の行は、どれか 1 つの任務が求める最大数を取る。
  各任務が艦を必要とするのはその任務の時点だけで、艦は手元に残るからである(近代化改修の素材と 改修素材 は消費するので合計する)。
  装備は交換、変換、廃棄で消費するので合計する。
  数はプレーンテキストで出し、不足だけを目立たせる。
  「0/2」(所持/必要)のような不足は赤で、それ以外は必要数を薄く出す(「×4」。poi のデータがないときも同じ)。
  名前が解決できないときは「?/2」と出す。
  所持数は poi の艦と装備から数える(名前で指定した艦は、その後の改装形とも一致する。艦種名と艦級はマスターデータで解決する。オーバーライドで指定したマスター ID、艦種、艦級、装備カテゴリは厳密に一致させる)。
  艦娘 や 装備 のセクションが空なら出さない。
  その下に 後続任務(この任務で解放される任務)が並ぶ。

任務の状態(poi の状態の `quests`、protocol.ts の `PoiQuests`)のうち、達成 / 遂行中 / 受注可 はゲームの一覧をそのまま使う。
達成済(推定。一覧にある任務の祖先)と 未開放(推定。一覧にある一回限りの任務より後の任務)もある。
全て の一覧がないとき(poi を再起動してから任務画面を開いていない)は、poi が持つ受注中の任務だけから推定する。
poi がなければすべて 不明 になり、所持艦との照合もしない。

実施可能(`shared/quest/doable.ts` の `questDoability`)は、poi の任務の状態と所持リストがあるときだけ使える。

1. **解放済み:** 状態が 受注可、遂行中、達成 のいずれか(未達成 と 遂行中 のグループ)であること。
   不明 を解放済みとみなすのは、poi が 全て の一覧を見ておらず、かつ前提がすべて 達成済 と推定された任務だけである。
   全て の一覧があるときは、一覧にない任務は受注できない(クリア済みか、まだ出ていない)。
   前提のない任務は推定の手がかりがない。
   それ以外の 不明 の任務は除外して件数を出す(「不明 N 件は除外」)。
   推定で解放済みとした任務は、クリア済み(一回限り)か時期外(期間限定)の可能性があり、全て の一覧を開くと確定する。
2. **所持:** 任務自身の条件(オーバーライド、なければ kcwiki-quest-data)が挙げるすべての艦、艦種 / 艦級ごとの数、装備を、必要な数だけ持っていること。
   判定と数え方は 必要なもの と同じ(`aggregateRequirements`)だが、前提任務の分は数えない。
   `or` のリストはどれか 1 つの選択肢を満たせばよい(`and` / `then` のリストの中の `or` なら、1 つの組み合わせ)。
   満たさない任務には、いちばん近い選択肢の不足分を出す。
   レベル、★、熟練、艦隊内の位置は確認しない。
3. **条件未確認:** 構造化した条件がない任務、自由記述の `other` 条件を持つ任務、マスターデータにない名前を含む任務は確認できない。
   こうした任務も 実施可能 に数え、「条件未確認」の印を付ける(詳細にはその条件を列挙する)。

進捗のカウントは次のように出す。
poi は `assets/data/quest_goal.cson` に載っている任務(130 件。実質的にデイリー / ウィークリー / マンスリー / クォータリー / イヤリー)の関連イベントをすべて数えていて、`info.quests.records` に持っている。
タブは数え直さず、そのカウント(たとえば `2/5`。サブゴールごとに 1 つ)を出す。
poi が追跡しない受注中の任務は、手書きのオーバーライド(`shared/quest/overrides.json`)にある機械的な条件(マップごとのボス / ノードでのランクと艦隊の確認、演習、遠征、廃棄、...)をプラグインが自分で数え、`source: "kcsim"` の `records` のゴールとして送る。
タブはそれらに「進捗 (kc-sim)」のラベルを付け、サブゴールごとに 1 行ずつ並べる。
それ以外の任務には、ゲーム自身の `api_progress_flag`(50% / 80%)か 達成 を出す。

## デザインシステム

トークンは `src/styles.css`(`@theme`)に、基本部品は `src/ui` にある。
アイコンは `lucide-react`(インライン SVG、`currentColor`。プラグインの CSS のスコープ下でも動く)と、`ui/EquipIcon`(`api_type[3]` ごとに自前で描いた装備カテゴリのグリフ)を使う。

- 間隔は 4 / 8 / 12 / 16 / 24 px(`1 2 3 4 6`)。角丸は `rounded-md` の 1 種類だけで、`rounded-full` はメーターとドットにだけ使う。
- 面の階層は、ページ `ink-950` → パネル `ink-900`(`Card`。枠は全周のヘアライン `ink-800`)→ 浮き上がった要素とコントロール `ink-800`。ボックスに片側だけの枠線、内側の影の縞、角の装飾は付けない。リストの項目は、間隔か全幅のヘアラインで区切る。
- 文字サイズは `xs` 11px(キャプション、列見出し)、`sm` 13px(本文)、`base` 14px(タイトル)、`lg` 20px(主要な数値)。数値は等幅にして列で右揃えにし、単位は数値のすぐ後ろに置く。
- 色は意味を表すときだけ使う。`accent` = 操作可能/選択中、`rank-*` = 戦闘ランク、`hp-*` = 損傷状態、ノードの色 = ノードの種類、`danger` = 失敗。グラデーション、グロー、OK/NG の色付き枠、装飾的なバッジ、絵文字は使わない。
- 状態は色付きの枠ではなく、アイコンの形と色か、データのバーで示す。

## poi のデータ

| ページが動く場所 | poi の状態 |
|---|---|
| プラグインの iframe 内 | プラグインから受け取る(`src/poiBridge.ts`) |
| 通常のブラウザ | なし。プリセットは JSON で取り込める。出撃タブで「内蔵サンプルデータを使う」を選べる(同梱のサンプルの艦と装備。オンの間は 設定 の歯車にスイッチを出す) |
| 親ページなしの `bun run dev` | `myState.json`(ダンプした poi の状態。gitignore 済み)か `src/sampleState.json` を `/__dev/state.json` で配信する |

プリセットと設定は、このオリジンの localStorage(`kcsim:*`)に保存する。
